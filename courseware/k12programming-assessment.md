# Python
## 一、方法概述

本方法是**给定学生已完成的Python代码作品**（如课堂作业、项目源码），通过**代码静态分析 + 结构化提问 + 代码重构任务**三种手段，反推并评估学生在编写该代码时体现出的分解、抽象、模式识别、算法设计四种计算思维能力。

**适用场景**：期末作品评审、编程作业批改、学习过程档案袋评价（Portfolio Assessment）。



## 二、总体流程

```
已有代码 → ①代码结构分析（教师/工具） → ②计算思维特征提取
        → ③面向学生的诊断性提问 → ④要求学生修改/重构代码
        → ⑤综合评分
```



## 三、分维度评测设计（基于已有代码）

### 1. 分解能力评测——看"模块划分痕迹"

**分析对象**：代码的函数/类结构、代码行数分布、是否存在"一个函数干所有事"的现象。

**具体做法**：

**步骤1：结构画像**
教师（或简单静态分析脚本）统计学生代码的以下指标：

| 指标 | 说明 |
|---|---|
| 函数/方法数量 | 是否只有一个 `main` 承担所有逻辑 |
| 最长函数行数 | 超过30行提示分解不足 |
| 函数职责单一性 | 一个函数是否同时做"输入+计算+输出" |
| 重复代码块数量 | 相似代码是否被提取为函数 |

**示例代码片段（学生原始代码）**：
```python
def main():
    data = input("请输入成绩，用逗号分隔：")
    nums = data.split(",")
    total = 0
    for n in nums:
        total += int(n)
    avg = total / len(nums)
    if avg >= 90:
        print("优秀")
    elif avg >= 60:
        print("及格")
    else:
        print("不及格")
main()
```

**诊断性提问（面向学生）**：
> "这段代码里包含了几个不同的任务？如果要新增'统计最高分'的功能，你会在哪里改？会不会影响其他部分？"

**评分标准**：

| 等级 | 描述 |
|---|---|
| 优秀 | 学生能准确指出代码中隐含的"读取-计算-判断-输出"多个子任务，并能说明当前代码未做拆分的风险 |
| 中等 | 能识别部分任务边界，但说不清耦合的影响 |
| 待提高 | 认为代码"能跑就是一个整体"，无分解意识 |

**重构任务（验证是否真正理解）**：
要求学生将上述代码改写为多个函数：`read_scores()`、`compute_average(scores)`、`grade_level(avg)`，并观察其重构后代码的接口设计是否合理。



### 2. 抽象能力评测——看"数据建模是否恰当"

**分析对象**：变量设计、数据结构选择、命名语义化程度。

**具体做法**：

**步骤1：提取代码中的数据结构使用情况**

**示例代码（学生原始代码，抽象水平较低）**：
```python
name1 = "张三"
chinese1 = 90
math1 = 85
name2 = "李四"
chinese2 = 88
math2 = 92

print(name1, (chinese1+math1)/2)
print(name2, (chinese2+math2)/2)
```

**诊断性提问**：
> "如果班里有50个学生，你的代码要写多少行变量？有没有办法用一种结构，把'一个学生的所有信息'打包在一起？"

**评分标准**：

| 维度 | 低水平表现 | 高水平表现 |
|---|---|---|
| 数据组织 | 用并列变量（name1, name2...）表示同类数据 | 用列表/字典/类统一表示 |
| 命名语义 | `a`, `b`, `x1` 等无意义命名 | `student_name`, `avg_score` 等语义清晰命名 |
| 通用性 | 只能处理固定2个学生 | 数据结构可扩展到任意数量 |

**重构任务**：
要求学生用字典列表或自定义类改写上面代码，评估其能否完成"从具体实例到通用模型"的抽象跃迁：
```python
students = [
    {"name": "张三", "scores": [90, 85]},
    {"name": "李四", "scores": [88, 92]},
]
for s in students:
    print(s["name"], sum(s["scores"]) / len(s["scores"]))
```



### 3. 模式识别能力评测——看"是否用统一逻辑处理相似问题"

**分析对象**：代码中是否存在**结构相似但被重复手写**的代码块（即"复制粘贴式编程"的痕迹），以及是否使用了Python的惯用模式（循环、列表推导式、内置函数）。

**具体做法**：

**示例代码（存在明显重复模式未被识别）**：
```python
even_list = []
for i in range(1, 21):
    if i % 2 == 0:
        even_list.append(i)

odd_list = []
for i in range(1, 21):
    if i % 2 != 0:
        odd_list.append(i)

square_list = []
for i in range(1, 21):
    square_list.append(i ** 2)
```

**诊断性提问**：
> "这三段代码的结构有什么共同点？能不能设计一个通用的'筛选/映射'函数，通过传入不同条件来复用？"

**评分标准**：

| 等级 | 表现 |
|---|---|
| 优秀 | 能指出三段代码均为"遍历+条件/变换"模式，能重构为参数化函数或使用 `filter`/`map`/列表推导式 |
| 中等 | 能发现代码重复，但只是简单复制而非抽取通用模式 |
| 待提高 | 意识不到代码存在结构性重复 |

**重构任务**：
```python
def filter_by(lst, condition):
    return [x for x in lst if condition(x)]

even_list = filter_by(range(1, 21), lambda x: x % 2 == 0)
odd_list  = filter_by(range(1, 21), lambda x: x % 2 != 0)
```

观察学生能否独立完成，或在提示后能否理解并解释该重构的意义。



### 4. 算法能力评测——看"正确性、边界处理与效率意识"

**分析对象**：代码的逻辑正确性、异常/边界处理、复杂度。

**具体做法**：

**步骤1：设计"陷阱测试用例"**，用学生代码运行，观察是否报错或结果错误。

**示例代码（学生原始代码，隐藏漏洞）**：
```python
def find_max(lst):
    max_val = 0
    for n in lst:
        if n > max_val:
            max_val = n
    return max_val
```

**评测用例设计**：

| 测试用例 | 目的 | 预期暴露的问题 |
|---|---|---|
| `[-5, -2, -8]` | 全负数 | 初始值为0导致结果错误 |
| `[]` | 空列表 | 无异常处理，直接返回0（错误但不报错，隐蔽性强） |
| `[3]` | 单元素 | 检验基本正确性 |
| 长度为10万的列表 | 效率测试 | 观察运行时间，考察是否有更优算法意识 |

**诊断性提问**：
> "如果传入的列表全是负数，你的代码结果对吗？为什么？如果传入空列表呢？"

**评分标准**：

| 维度 | 评分要点 |
|---|---|
| 正确性 | 能否自己发现初始值设置错误（应使用 `lst[0]` 或 `float('-inf')`） |
| 边界意识 | 能否主动提出对空列表、单元素等情况加判断 |
| 效率意识 | 面对大数据量，能否讨论时间复杂度，而非仅满足于"能出结果" |



## 四、综合评分表（整合四维度，基于已有代码）

| 计算思维维度 | 评测手段 | 权重 | 评分依据 |
|---|---|---|---|
| 分解 | 结构分析 + 重构任务 | 25% | 函数划分合理性、职责单一性 |
| 抽象 | 数据结构分析 + 提问 | 25% | 数据建模合理性、命名语义化 |
| 模式识别 | 重复代码检测 + 重构任务 | 25% | 能否归纳通用逻辑、使用Python惯用法 |
| 算法 | 陷阱测试用例 + 提问 | 25% | 正确性、边界处理、效率意识 |

**总分计算方式**：
$$
\text{总分} = 0.25S_{分解} + 0.25S_{抽象} + 0.25S_{模式} + 0.25S_{算法}
$$

每个子项可按四级量表（优秀4分/良好3分/合格2分/待提高1分）评分后加权求和。


## 五、方法优势

1. **贴近真实学习场景**：学生的日常作业、项目代码天然存在，不需要额外设计新任务，评测更自然、成本更低
2. **暴露真实思维水平**：相比"命题写代码"，学生在完成自己感兴趣的项目时更容易暴露真实的分解、抽象习惯，而非应试性套用模板
3. **"诊断+重构"双验证机制**：仅靠提问可能被"背答案"，因此设计**必须动手重构代码**的环节，确保评测的是真实能力而非语言表达
4. **可操作性强**：教师可用简单脚本（如统计函数数量、圈复杂度、重复代码率）辅助人工评分，具备一定的自动化潜力



## 六、实施建议

- **建立学生代码成长档案袋**：定期收集学生代码，用此方法纵向比较其计算思维发展轨迹，而非仅做一次性终结性评价
- **教师培训**：需要教师具备识别"代码坏味道（code smell）"与计算思维要素对应关系的能力
- **工具辅助**：可借助 `radon`（圈复杂度分析）、`pylint`（代码规范/重复检测）等工具辅助识别分解和模式识别维度的问题，减轻人工分析负担
